# Hugo Refactoring Plans

Generated by the improve skill on July 27, 2026, against commit `c047d57`.
These plans turn the current mixed `Screens`/`Features`/`Views`/`Managers`
layout into a feature-first SwiftUI application while preserving SwiftData and
CloudKit compatibility.

Execute the plans in order. Each executor must read its plan completely, honor
its STOP conditions, run every verification gate, and update the status below.

```text
        Legacy/

        Categories/
        Entries/
        Onboarding/
        Overview/
        Reports/
        Settings/
    Shared/
        SymbolPicker/
    PreviewSupport/
    Resources/
Configuration/
HugoTests/
    Domain/
    Features/
    Persistence/
    TestSupport/
```

The project remains one application target. Do not introduce packages,
repositories, coordinators, dependency-injection frameworks, or a ViewModel for
every view. SwiftUI views should own ephemeral presentation state; pure structs
should own deterministic calculations; `@Observable` reference types are for
stateful workflows such as add/edit forms and app bootstrap state.

## Dependency notes

* Plan 001 must land first because the existing test suite contains only an empty template test.
* Plan 002 removes disconnected files before file moves, preventing dead code from being carried into the new hierarchy.
* Plan 003 preserves the SwiftData schema and migration chain before feature code is renamed or relocated.
* Plan 004 gives reports and later overview work one tested aggregation layer instead of calculations embedded in views.
* Plan 005 establishes `Category*` UI names while explicitly retaining the persisted `Tracker` model identity.
* Plan 006 consumes the category picker and default-category behavior established by Plan 005.
* Plan 007 consumes the add-entry and reporting domain APIs established by Plans 004 and 006.
* Plan 008 enables Swift 6 only after mutable async code has been isolated behind testable boundaries.
* Plan 009 is intentionally last because formatting and project-file cleanup should operate on final paths.
* Plan 014 is a correctness fix to plan 012's `SubmittedReport` model (not CloudKit-eligible → schema never pushed, production sync fails). It edits V9 in place because the fix is optionality-only and V9 never reached CloudKit or users; it depends on 012 being DONE and must land before any build that ships V9 to Production.
* Plan 015 supersedes 014 after the in-place edit proved unsafe: making `SubmittedReport` optional changed the entity version hash, so existing V9 stores (iPhone TestFlight build, simulators) fail to open with `loadIssueModelContainer` ("Cannot use staged migration with an unknown model version", NSCocoaErrorDomain 134504). 015 keeps V9 frozen at its deployed shape, adds SchemaV10 (7.0.0) with the eligible all-optional model, and re-stamps existing stores via a lightweight V9→V10 migration. The in-place submission update and optional-chaining read fixes from 014 are kept (they target the shared `SubmittedReport` typealias, now V10).

## Architecture decisions

* Organize source by feature, not by React-like technical buckets such as `Views`, `Structs`, `Enums`, and `Managers`.
* Keep SwiftData queries at feature boundaries. Do not add a repository layer merely to hide `@Query` or `ModelContext`.
* Use explicit top-level Swift type names instead of empty namespace structs such as `EntryList` and `EntrySheet`.
* Use `View` as the suffix for SwiftUI types. Names should describe responsibility: `AddEntryView`, `EntryRow`, `MonthlyReportDetailView`.
* Use “Category” in user-interface and feature names because the product already localizes trackers as categories. Keep `SchemaV*.Tracker`, `Entry.tracker`, and CloudKit record identities unchanged unless a separately designed data migration is approved.
* Preserve every historical schema type needed to open existing stores. A file that is unused by current UI is not dead if `HugoMigrationPlan` references its schema.
* Prefer pure value types for report aggregation, date ranges, status thresholds, and formatting. Use `@Observable` only where mutable workflow state benefits from a reference identity.

## Findings considered and rejected

* Splitting `SymbolSet.swift` solely because it is 275 lines: rejected. Most of the file is static catalog data; rename it to `SymbolCatalog.swift`, but do not fragment one coherent catalog without a product-level grouping.
* Introducing Clean Architecture, coordinators, repositories, or Swift packages: rejected. The app is roughly 6,100 lines in one target, and those layers would add indirection without an isolation or reuse benefit.
* Deleting historical `SchemaV1`–`SchemaV7` models as “unused”: rejected. They are required by the declared migration chain and existing user stores.
* Renaming the persisted SwiftData `Tracker` model to `Category` during this refactor: rejected. CloudKit and migration compatibility make that a separate data-model project; this refactor limits the rename to UI/domain-facing symbols.
* Deleting the empty `SchemaV8.Report` immediately: rejected. It is migration ballast from the recent report-to-entry transition. Plan 003 documents it and removes the current alias, but a future schema version must prove safe removal with migration fixtures.
